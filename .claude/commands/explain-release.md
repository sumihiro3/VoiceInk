# /explain-release — リリース解説レポート(HTML)

run-release が作った変更を、レビューする人のために 1 枚の HTML で解説する。目的は 2 つ: (1) 何がどう実装されたかを差分を読む前に理解できるようにする (2) **人が確認すべきポイントを優先度つきでハイライトし、確認手順まで示す**。

引数: `$ARGUMENTS`(リリース識別子。省略時は現在のブランチ名)

## 起動される場面

- `/run-release`・`/refine-requirements` が run-release の戻り値(完了・停止のいずれも)を受け取った直後。`config.report.enabled` が `false` でない限り必ず実行する
- 後から単独で。戻り値が手元に無い場合(セッション切れ等)は「材料の集め方」の再構成列を使う

## 進め方

1. **config の読込**: `.claude/workflow.config.json` を Read する。`baseBranch`・`requirementsPath`・`knownIssues.path`・`conventionsDoc`・`syncDocs.targets`・`automation.stateDir`・`report` を使う。パスを本文にハードコードしない
2. **材料を集める**: 後述の表に従う。戻り値にあるものは戻り値を正とし、無いものだけ再構成する。差分が大きい場合(目安: 変更 30 ファイル超または 2000 行超)は、FR 単位でサブエージェントに読解を委譲し、メインは統合と HTML 生成に専念する
3. **ハイライトを抽出する**: 後述の「ハイライトの抽出規則」を機械的に適用する。優先度の判断を感覚で行わない
4. **HTML を書く**: 後述の「HTML の要件」に従い、出力先へ書き出す
5. **検証する**: 後述の「検証」を実施し、不合格なら直してから報告する
6. **報告する**: 出力パス、開き方、**必須ハイライトの一覧(1 件 1 行)**を会話に書く。HTML を開かなくても何を確認すべきかが分かるようにする。セッションがファイルを提示する手段(アーティファクト、ファイル送信等)を提供していればそれも使う。PR があれば、最後に「確認を済ませて PR をマージしたら `/close-release`」と添える

## 出力先

- 既定: run の state ディレクトリ(`config.automation.stateDir` があればその配下、無ければ `${TMPDIR:-/tmp}/claude-release-workflow/<リポジトリ名>/<release>/`)の `report.html`。OS の一時領域は数日で消えうる旨を報告に添える
- `config.report.outputDir` がある場合は `<outputDir>/<release>/report.html`
- **リポジトリ内へ出力する場合は `git check-ignore` で無視対象であることを確認する。** 無視されていなければ既定の出力先へ倒し、その旨を報告する(未追跡ファイルが残ると次回 run-release の Gate 0 クリーンツリー検査で拒否されるため)
- 再実行時は上書きする

## 材料の集め方

| 材料 | 一次ソース(戻り値) | 戻り値が無い・欠けるときの再構成 |
| --- | --- | --- |
| 終了区分・PR | `status`・`prUrl`・`stopReason`・`reportMaterial.isDraft`・`reportMaterial.draftReasons` | `gh pr view --json url,isDraft,title,body`、state.json の `phase` |
| AC 充足 | `reportMaterial.acVerification.items` | PR 本文の AC 表。無ければ requirements.md の AC を列挙し「未検証」と表示 |
| 最終検査 | `reportMaterial.finalCheck` | PR 本文 |
| レビュー | `reportMaterial.reviewFixed`・`residualFindings`・`fixWaived`・`unverifiableDimensions`・`codexReview`・`reviewPrecision`・`severityChanges`・`checkFixed` | PR 本文、state.json の `codexRounds` |
| 実装メモ | `reportMaterial.implementation`(作業単位ごとの報告・判断に迷った点・衝突候補) | 再構成不可。「取得できず」と表示 |
| 起票 | `filedIssues`・`resolvedKnownIssues`・`resolvedLogProposal` | `git diff <baseBranch>...HEAD -- <knownIssues.path>` |
| コミット・差分 | `commitPlan` | `git log --reverse --stat <baseBranch>..HEAD`、`git diff --stat <baseBranch>...HEAD`。PR がマージ済みで両方とも空になるときは、`gh pr view --json baseRefOid,headRefOid` の 2 点間で取る |
| 要件 | requirements.md(FR・AC・スコープ外・未解決事項) | 同左 |
| 要件書への指摘 | `reportMaterial.requirementIssues`・`requirementEdits` | PR 本文の「要件書について人の判断が要る点」。旧エンジンの run では「取得できず」 |
| リリース外のファイル | `reportMaterial.foreignFiles`(コミット直前停止では戻り値の `foreignFiles`) | PR 本文の「コミットしなかったファイル」。旧エンジンの run では「取得できず」 |
| 手動検証 | requirements.md と同じディレクトリの `e2e-verification.md`(導入先が別名で運用していることがある。無ければ同じディレクトリで「(手動検証必須)」の AC を扱う文書を探す) | 同左(見つからなければ「未作成」) |
| 消費 | `reportMaterial.consumption`(工程名は読者向け)・`reportMaterial.totalAgents` | 戻り値の `consumption`(内部名。README の「用語」で言い換える)、state.json の `consumption`・`totalAgents` |

`reportMaterial` を返さない旧エンジンの戻り値では、`prBodyDraft` を読み、足りない分を再構成する。再構成で埋めた節には「再構成」と表示する。

## ハイライトの抽出規則

各ハイライトは ID(H-01 からの連番)・優先度・見出し・**なぜ確認が要るか**・**どこ**(ファイルと行、PR があれば `<prUrl>/files` へのリンク)・**どう確認するか**(実行できるコマンドまたは具体的な手順と期待結果)・**根拠**(どの材料から導いたか)を持つ。

| 優先度 | 対象(該当するものは全件) |
| --- | --- |
| **必須**(マージ前に確認) | 残存所見の critical / high(`residualFindings`)／修正不要と申告された所見(`fixWaived`。独立検証なし)／手動検証必須 AC の未実施(`manualPendingAcs`。e2e-verification.md の手順を転記)／AC 充足検証で未充足・検証不能の AC(`unmetAcs` を含む)／文書同期が更新したと報告したのに差分が無い文書(`syncUnverified`)／最終検査の失敗・収束不能／人の判断が要る要件書への指摘(`requirementIssues`。要件を直すか実装を直すかを決める)と、修正エージェントが要件ファイルを書き換えたので元に戻した記録(`requirementEdits`)／同一バッチ内で複数の作業単位が同じファイルを書いた衝突候補(`implementation.sameBatchCollisions`)／報告と実差分の不一致(`implementation.unverifiedFiles`)／実装に失敗した作業項目(`failedItems`)／draft 降格・停止の理由(`draftReasons`・`stopReason`)のうち、ここまでの項目で説明のつかないもの(例: 残存所見が無いままのレビューループ収束不能)／権限・秘密情報・依存・CI に関わる変更(.gitignore、設定ファイル、依存マニフェストやロックファイル、ワークフロー定義、ライセンス)／要件の「場所」にも「スコープ外」にも説明のつかないファイルへの変更(文書同期の対象 `syncDocs.targets`・`knownIssues.path`・要件ファイルのディレクトリは run 自身が書くので説明がつく) |
| **推奨** | 新規起票された既知課題のうち medium 以上／検証不能だったレビュー次元(`unverifiableDimensions`)／Codex を使えなかった周(`codexReview` の used 以外)／検証エージェントが深刻度を改めた所見(`severityChanges`。特に下げたもの)／修正回数の上限に達した周で初めて検出され、修正を試していない残存所見／文書同期に失敗した対象／コミットしなかったリリース外のファイル(`foreignFiles`。run の途中で追加された未追跡ファイル。作業ツリーに残っている)／実装メモの「判断に迷った点」／要件の「未解決事項」に対して実装が下した決定／新規ロジックに対応するテストが見当たらない箇所 |
| **参考** | 複数の作業単位が逐次に触ったファイル(`implementation.multiTouchedFiles`。結線ファイルなら想定内。`sameBatchCollisions` にも載っているファイルは必須側で扱い、ここには重ねない)／消費の偏り(特定フェーズへの集中、上限の 8 割超)／`resolvedLogProposal`／レビューの精度(`reviewPrecision`。棄却の多い観点は観点の指示を見直す候補) |

- 必須は全件を載せる。推奨は重要な順に最大 10 件、超過分は件数だけ示す。参考は折りたたむ
- 確認方法が同じ対象(例: 説明のつかないファイル群)は 1 枚にまとめてよい。その場合も対象は「どこ」に全件列挙する
- 必須が 6 件を超えるときは、種類別の小見出しで区切る(例: 食い違い／残存所見／権限・秘密情報・依存・CI・設定／手動検証)。同型のカードが続くと流し読みできない
- カードの見出しは「何を確認するのか」が 1 行で分かる形にする(「〜が〜になっていることを確認する」)。事象の名前だけにしない。「なぜ」は 2 文以内に収め、長くなる経緯は FR の解説へ回して ID でリンクする
- 該当が 0 件の優先度は「該当なし」と明示する(空欄にしない。「無かった」と「調べていない」を区別する)
- 材料から導けないことをハイライトにしない。推測で不安を煽らない

## HTML の要件

- **単一ファイルで自己完結**。CSS はインライン。外部 CDN・Web フォント・外部画像・外部スクリプトを読み込まない(オフラインで開ける)
- JavaScript は任意。使う場合もインラインのみで、無効でも全内容が読めること(チェック状態の保存程度に留める)
- `prefers-color-scheme` でライトとダークの両方に対応する。印刷しても読める
- `<html lang>` は `config.language`。本文もその言語で書く
- **本文に、ワークフローの内部の言い方(残存・収束不能・Gate 0〜2・周・修正エージェントなど)と、戻り値のフィールド名(`residualFindings` など)を書かない。** README の「用語」の表の右の列の言い方にする。「根拠」の欄も同じ(例: 「residualFindings」ではなく「レビューで修正されずに残った指摘」)
- コード・差分の引用は HTML エスケープし、1 箇所 15 行以内。**gitignore 対象ファイルの内容、トークン、パスワード、鍵を引用しない**
- 図は後述の「図の規則」に従う。確認点の見せ方は後述の「確認点の見せ方」に従う

### 構成(この順)

1. **結論バナー**: リリース識別子、終了区分、PR リンク、draft 理由または停止理由、必須・推奨・参考の件数。直下に**必須の早見表**(後述)を置く
2. **確認してほしいポイント**: ハイライトを優先度順にカードで並べる。各カードにチェックボックスを付ける
3. **このリリースで何が変わったか**: 背景と目的を 3〜5 文で。続けて全体像の図(図 1。主要モジュールとデータの流れ。このリリースで追加・変更した箇所と既存の箇所を見分けられるようにし、確認点のある箇所には ID を添える)
4. **FR ごとの解説**: 目的、実装の要点(どのファイルの何が、なぜそう書かれているか)、主なファイル、AC 充足表(充足・未充足・手動・検証不能)。仕組みが「図の規則」の条件に当たる FR は、節の中に図を置き、図の番号を引いて説明する。確認点に触れる箇所は「確認点の見せ方」に従って本文の中で目立たせる(節末に ID を並べるだけで済ませない)
5. **品質ゲートの経過**: 検査ループとレビューループの周回、直した所見(`reviewFixed`)、Codex 委譲の表。ゲートを通った順と結果(通過・修正して通過・上限到達・残存)は進行図にする(周回数が取れなければ、分かっている範囲で描き「取得できず」を図中に書く)
6. **コミットと差分**: コミット一覧と各コミットの要約、変更規模
7. **既知課題**: 新規起票、追記、解決済みへ移動した ID
8. **消費**: フェーズ別のエージェント起動数
9. **次にやること**: マージ前チェックリスト(必須ハイライトの再掲)、手動検証の手順、次リリースへの申し送り

### ハイライトの見た目(統一する)

```html
<article class="hl hl-must" id="H-01">
  <header><label><input type="checkbox"> <span class="badge">必須</span> H-01 見出し</label></header>
  <p class="ask">確認すること: …(1 文。読んだ人が次に取る行動)</p>
  <dl>
    <dt>なぜ</dt><dd>…</dd>
    <dt>どこ</dt><dd><code>path/to/file:123</code> <a href="…/files">PR の差分</a></dd>
    <dt>確認方法</dt><dd><pre><code>実行できるコマンド</code></pre>期待結果: …</dd>
    <dt>根拠</dt><dd>レビューで修正されずに残った指摘 / 差分の実査 など</dd>
  </dl>
</article>
```

クラスは `hl-must`(必須)・`hl-should`(推奨)・`hl-info`(参考)の 3 種。左の太い縁・カードの薄い地色・バッジの色で区別し、色だけに頼らずバッジの文字でも区別する。`<p class="ask">` はカードの中でいちばん目立たせる(太字・やや大きく)。「なぜ」「根拠」はその後に続ける。

### 確認点の見せ方

確認点は「確認してほしいポイント」の節に集めるだけでなく、**読む人がその話題に出会った場所で目に入る**ようにする。

- **必須の早見表**: 結論バナーの直下に、必須ハイライトを 1 件 1 行で並べる(`<table id="must-summary">`。列は ID・確認すること・どこ)。各行の ID はカードへリンクする。カードを読まなくても、何件・何を見ればよいかが 10 秒で分かること。必須が 0 件なら「必須の確認点はありません」と書く
- **本文の中**: 確認点に触れる文は、対象の語句そのもの(ファイル名・条件式・AC 番号・設定値)を `<mark>` で包み、直後にハイライト ID へのリンクを置く。ID のリンクだけを置いて、対象の語句を素の文のままにしない
- **必須ハイライトは全件、その文脈を説明する節(FR の解説・品質ゲート・コミットと差分・既知課題のいずれか)から少なくとも 1 回参照される**こと。形は本文の `<mark>`・注意書き・表のバッジ・図のラベルのどれでもよい(同型の確認点が並ぶ手動検証 AC は、AC 充足表のバッジで足りる)
- **注意書き**: FR の解説の中で必須の確認点に当たる段落の直後には、注意書き(`<aside class="callout">`。「要確認」の文字・ID・確認することの 1 文)を置く。推奨・参考は `<mark>` とリンクだけでよい
- **表の中**: AC 充足表・ファイル一覧・コミット一覧で確認点に対応する行は、行を薄く色づけ、「要確認 H-xx」のバッジを付ける
- **図の中**: 確認点のある箇所は、図中の該当ノードに ID を添える(図を見ただけで、どこを確認するのかが分かる)
- 目立たせるのは確認点だけにする。強調が多いと確認点が埋もれるので、確認点でない箇所に `<mark>` や注意書きを使わない

### 図の規則

説明が込み入ってきたら、文章を足さずに図を足す。**図を置くかどうかは感覚で決めず、次のいずれかに当たれば必ず置く。**

| 条件 | 図の型 |
| --- | --- |
| 発火・分岐の条件が 3 つ以上ある(例: 複数の条件がすべて揃ったときだけ動く処理) | 分岐図 |
| 処理が 4 段以上の順序を持つ、または 3 つ以上のモジュール・ファイル・外部サービスを跨いでデータや制御が流れる | 流れ図 |
| 状態の遷移・リトライ・複数ラウンドの進行がある(品質ゲートの経過を含む) | 進行図 |
| 構造が変わった(ファイルの移動・責務の付け替え・インターフェースの変更) | 前後比較図 |
| 1 つの仕組みの説明が 5 文を超える | 上のうち最も近い型。図を置いたうえで文章を削る |

- 図は説明の前に置き、本文は図中の番号(①②…)を引いて説明する。本文からは「図 N」とリンク(`href="#fig-N"`)で参照する。本文から参照されない図は置かない
- `<figure id="fig-N">` に `<figcaption>`(「図 N: 何の図か」)を付ける。インライン SVG(または HTML/CSS)で描き、SVG には `<title>` と `<desc>` を付ける
- 1 枚の図のノードは 9 個まで。超えるなら図を分ける。文字は 11px 以上。狭い画面では図だけを横スクロールさせ、ページ全体を横スクロールさせない
- 色は CSS 変数で指定し、ライトとダークの両方で読めること。凡例を付け、色だけでなく線の太さや文字でも区別する。**強調の意味は図ごとに凡例へ書く**(仕組みの図: このリリースで追加・変更した箇所／既存のまま。進行図: すんなり通らなかった工程／通過した工程。どの図でも: 確認点あり)
- 装飾目的の図、本文と同じことを言い直すだけの図は置かない

## 正確性の規約

- 記述はすべて材料(戻り値、git、読んだファイル)に基づく。確認していないことを断定しない。取得できなかった材料は「取得できず」と書く
- 戻り値・PR 本文と実際のリポジトリが食い違ったら(例: `prUrl` があるのに PR が見つからない、PR 本文が同期済みとする文書に差分が無い、起票済みとされた既知課題が既に解決済みログにある)、食い違い自体を必須ハイライトにする。PR 本文は run の時点の記録で、後続のコミットで古くなる
- run が途中で止まっている場合は、どの工程まで進んだか(state.json の `phase`)と、作業ツリーに残っている未コミット変更を冒頭で示す

## 検証

- 出力ファイルが存在し空でない
- `class="hl ` の出現数が、抽出したハイライト件数と一致する
- 本文中の `href="#…"` がすべて実在する `id` を指す
- `src="http`・`<link ` ・`@import` が無い(外部リソースを読み込んでいない)
- テンプレートの置換漏れ(`{{`、`TODO`、`…` のままの項目)が無い
- 会話に書く必須ハイライト一覧と、HTML の必須カードが 1 対 1 で対応する
- 必須の早見表(`id="must-summary"`)の行数が必須件数と一致する
- 必須の各 ID が、「確認してほしいポイント」の節と早見表と「次にやること」以外の節から、少なくとも 1 回 `href="#H-xx"` で参照されている
- `<mark>` が 1 つ以上あり、すべての `<mark>` の直後にハイライト ID へのリンクがある(確認点でない箇所を強調していない)
- すべての `<figure id="fig-N">` に `<figcaption>` があり、本文から `href="#fig-N"` で 1 回以上参照されている
- 「図の規則」の条件に当たると判定した節に `<figure` がある(判定した節と条件を、報告に 1 行ずつ書く)

## 注意

- このコマンドはリポジトリの追跡ファイルを変更しない。コミットも push もしない
- 検査コマンド・文書パス等の固有値をこのコマンド本文に書き写さない(常に config を正とする)
